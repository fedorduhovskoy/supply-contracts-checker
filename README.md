# Проверка условий договоров поставки (прототип)

Загружаешь TXT-файлы → получаешь таблицу «договор / поставщик / сумма / срок поставки на дату проверки» (по умолчанию 10.03.2026).
Каждое значение — с файлом, дословной цитатой и переходом к абзацу. Неподписанные проекты и предложения из писем показываются отдельно как «не согласовано» и в значения не попадают.

## Запуск

```bash
pip install -r requirements.txt
python3 -m uvicorn server:app --port 8099      # открыть http://localhost:8099
python3 -m pytest -q                           # 12 тестов, без сети и ключей
```

Кнопка «Загрузить примеры» берёт 6 файлов из `documents/`, либо перетащите свои `.txt`.

**Два режима** (переключаются сами):

| Режим | Когда | Что делает |
|---|---|---|
| **stub** (по умолчанию) | ключ не указан | Извлечение правилами/регулярками. Платный API не нужен. Заточен под формат учебных договоров («Общая стоимость… рублей», «поставить… не позднее ДД.ММ.ГГГГ», строка «Статус:») |
| **LLM** | в поле вверху вставлен API-ключ polza.ai (или env `POLZA_API_KEY`) | Модель `openai/gpt-6-luna` через OpenAI-совместимый прокси `https://api.polza.ai/api/v1`. Меняется в «настройки LLM» или env `LLM_BASE_URL`, `LLM_MODEL` |

Ключ уходит только на локальный сервер и дальше в прокси, в код и на диск не пишется. Разбор 6 файлов в LLM-режиме ≈ 0,12 ₽.

## Примеры

- STN-101: 1 380 000 ₽, срок **30.04.2026** — изменено допсоглашением №1 (оригинал 1 200 000 / 15.04). Проект №2 (1 450 000 / 10.05) — «не согласовано».
- STN-102: 840 000 ₽ (не аванс 252 000), срок 20.03.2026; предложение поставщика о 27.03 — «не согласовано».
- STN-103: сумма **нет данных** (600 000 — лимит бюджета, не цена), срок 30.04.2026.
- Вопрос «поставка раньше 1 апреля»: только STN-102, и по нему есть несогласованное предложение 27.03.

## Архитектура

```
TXT → абзацы (файл+№) → экстрактор (stub | LLM) → verify (цитата есть в тексте, значение есть в цитате)
    → resolve (код: действует подписанное допсоглашение с датой вступления ≤ даты проверки) → таблица / ответы / источник
```

Файлы: `textnav.py` (всё ядро), `server.py` (FastAPI), `static/index.html` (UI без сборки), `tests/`.

Три ключевых решения:
1. **Модель извлекает, код решает.** LLM возвращает факты с цитатами; какое значение действует, определяет детерминированный `resolve`. Плюс: воспроизводимо, тестируется, правило «меняет только подписанное и вступившее в силу» не зависит от настроения модели. Минус: новые типы связей (ссылки на пункты, цепочки допсоглашений) надо кодировать.
2. **Цитата как контракт.** Факт без дословной цитаты, найденной в абзаце, и без значения внутри цитаты отбрасывается («нет данных» + предупреждение). Это закрывает выдумки модели; цена — иногда теряем верное значение при неточной цитате (так и было, см. отчёт ниже).
3. **Stub с тем же форматом, что и LLM.** Весь остальной конвейер один; прототип работает без ключа и без платного аккаунта. Компромисс: stub хрупок к другим формулировкам — это явно помечено в UI.

## Допущения

- Одна строка файла = один абзац; ссылка = имя файла + номер абзаца.
- Допсоглашение действует, если подписано обеими сторонами и дата вступления в силу ≤ даты проверки; без даты вступления — «нужна проверка», не применяется.
- Договор к документам привязывается по номеру (`STN-101`); несколько допсоглашений применяются по дате вступления в силу, не по имени файла и не по дате загрузки.
- «Сумма» — итоговая стоимость договора; аванс, лимит бюджета и сроки оплаты не считаются.

## Записка

**Для кого.** Специалист по закупкам, сверяющий условия поставок без перечитывания документов.

**Пять вопросов клиенту.** (1) Какие ещё поля нужны, кроме суммы и срока (неустойка, оплата, НДС)? (2) Как выглядят реальные договоры: форматы, сканы, приложения со спецификациями? (3) Как определять вступление в силу, если дата не указана или есть «с момента подписания»? (4) Где хранятся документы и кто к чему имеет доступ? (5) Какая цена ошибки и кто проверяет — нужен ли аудит-след?

**Метрики.** (1) Доля значений с подтверждённой цитатой и верных при выборочной ручной проверке (точность и полнота по полям); (2) время закупщика на сверку одного договора до/после.

**При 100 000 документов и правах доступа.** Извлечение в очередь с кэшем по хэшу текста и версионированием схемы; хранилище фактов (Postgres) + индекс по абзацам; привязка документов к договорам по реквизитам, а не только по номеру; права — фильтрация на уровне запроса (ACL документа наследуется фактом), логирование обращений; вместо «загрузить и посмотреть» — пакетная обработка с очередью проверки для «нужна проверка».

**Следующие улучшения.** (1) Неустойка и условия оплаты с цитатами; (2) очередь «нужна проверка» с подтверждением человеком и обратной связью в оценку качества; (3) PDF/DOCX/OCR и спецификации-приложения.

## Известные ограничения

- Только TXT; без OCR и PDF/DOCX.
- Stub понимает только формулировки учебных документов; LLM-режим устойчивее, но зависит от модели и проверяется только цитатой.
- Нет ссылок на конкретный пункт договора внутри допсоглашения: считается, что «Пункт 2.1» = цена, «Пункт 3.1» = срок поставки.
- Заглушки: нет хранилища, нет авторизации, состояние живёт в браузере.

## Отчёт о вайбкодинге

Инструмент: Claude Code (модель Claude Sonnet 5.5). Фактические затраты времени и остаток задач — минут 20.

Характерные запросы: «разбери задание и файлы, предложи план»; «LLM через polza, openai-luna, ключ в UI, stub без ключа»; «сделай проверку цитат, чтобы нельзя было выдумать значение».

Ошибки ИИ и как поймали:
- Регулярка `общую? стоимост` не матчила «Общая стоимость» → у всех договоров сумма была «нет данных». Поймали юнит-тестами на реальных файлах (4 из 12 упали), исправили на `общ(?:ая|ую)`.
- Луна на договоре STN-103 процитировала не тот абзац как основание для поставщика. Verify отбросил значение с предупреждением; поправили промпт («цитата обязана содержать само значение») и повторили.
- Python с python.org на macOS без системных сертификатов → `CERTIFICATE_VERIFY_FAILED` при обращении к прокси. Подключили `certifi`.
